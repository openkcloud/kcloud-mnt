01요약

UI 목업뿐이던 openKcloud AI 노트북(AI 개발환경) 파트를 실제로 동작하는 시스템으로 전환했습니다. 사내 GPU 2장으로 Kubernetes 멀티노드 클러스터를 구성하고, Kubeflow 표준 스택 전체(Notebook·Profile·Pipelines·Katib·KServe)를 설치했으며, 포털과 클러스터를 잇는 CMP 백엔드를 신규 개발했습니다. 기획서의 핵심 사용자 여정이 포털 클릭만으로 전부 실행됩니다:

Profile 생성(쿼터 자동) → GPU 노트북 생성 → VSCode/Jupyter IDE 접속(인증)
→ Pipeline 업로드·실행 → HPO 자동 튜닝 → 모델 배포 → API 호출 → 성능 실측

이후 세 단계로 완성도를 높였습니다. ① 화면에 남아 있던 목업 수치를 전량 실측으로 전환, ② 학습부터 서비스 반영까지를 파이프라인 하나로 자동화하고 현장 데이터로 실제 모델을 만들어 서비스에 배포, ③ 세 번째 GPU 머신을 편입해 3노드·GPU 3장 멀티노드 체제로 확장. 이 상태로 두 차례 시연(경영진·원청)을 통해 전 기능을 실사용 조건에서 검증했고, 그 과정에서 드러난 안정성 이슈를 모두 해결해 반영했습니다(06절).

현장 데이터 실증 — 협력사 실제 생산라인의 DataMatrix 코드 이미지 5,651장(판독 성공 3,636 / 실패 2,015)으로 판정 모델을 학습해 검증 정확도 95.58%를 얻었고, 이 모델이 파이프라인을 통해 자동으로 서비스에 배포되어 32ms에 응답합니다. 예제 데이터가 아닌 실제 업무 데이터로 전 과정을 검증했습니다.

현장 데이터 학습 — DM코드 판독 가능성 판정 모델

협력사 생산라인의 DataMatrix 코드 이미지로 실제 모델을 학습했습니다. 판독기가 값을 읽어낸 사진(파일명에 코드값 포함)은 성공, 못 읽은 사진은 실패로 자동 라벨링되어 별도 작업 없이 학습 데이터가 확보됐습니다.

항목값
학습 데이터5,651장 (성공 3,636 / 실패 2,015)
모델 구조ResNet18 전이학습 · 5 epoch

이 모델은 코드 값을 읽는 것이 아니라 판독 가능 여부를 미리 판정합니다. 못 읽을 코드를 판독기까지 보내지 않고 촬영 직후 재촬영을 유도하는 것이 목적입니다.

학습 → 배포 자동화 (5단계 파이프라인)

prep(데이터 준비) → train(GPU 학습) → evaluate(성능 평가)
→ package(서빙용 포장) → deploy(서비스 반영)      총 76초

버튼 한 번으로 학습부터 서비스 반영까지 사람 손 없이 진행됩니다. 평가 단계 이후에만 배포가 실행되도록 순서를 걸어 검증되지 않은 모델이 나가지 않게 했습니다. 매일 새벽 자동 실행 예약도 등록되어 있어, 새 데이터가 쌓이면 밤사이 재학습됩니다.

HPO 실학습 전환

Katib Trial이 계산식으로 점수를 만들던 것을 실제 학습을 수행하도록 교체했습니다. 매 Trial이 DM코드 5,651장으로 ResNet18을 학습하고 검증 정확도를 반환합니다. 4회 탐색 결과 90.88~93.63%로 서로 다른 값이 나와 실학습임이 확인되며, 찾아낸 설정값(lr=0.000137, batch=32)과 탐색 범위를 화면에서 볼 수 있습니다.

연산별 핫스팟 프로파일링

ETRI 검토의견의 "병목 컴포넌트 식별"을 실측으로 충족했습니다. vLLM 내장 torch profiler를 요청 시에만 켜서 실제 추론을 추적하고, 트레이스의 self time을 집계해 연산별 소요시간을 산출합니다(상시 수집은 추론을 느리게 하므로 on-demand). GPU 커널 단위는 WSL 환경에서 CUPTI가 초기화되지 않아 수집되지 않으며, 이 제약을 화면에 명시했습니다. 표준 리눅스 클러스터에서는 동일 코드로 커널 단위까지 수집됩니다.

구성요소별 역할 — 무엇이 어떤 일을 하는가

구성요소역할왜 이것을 썼나
Kubernetes (k3s) 모든 워크로드(노트북·학습·서빙)의 실행 기반. 자원 스케줄링, 장애 시 자동 재기동, 멀티노드 확장을 담당 k3s는 K8s 표준 API를 그대로 제공하는 경량 배포판 — 개발 PC에서 검증한 매니페스트가 운영 클러스터(A100)에서 그대로 동작
Kubeflow K8s 위에 "ML 개발 플랫폼" 계층을 얹는 표준 스택. 본 시스템은 그중 Notebook·Profile 컨트롤러를 사용 — Notebook CRD를 만들면 컨트롤러가 Pod·Service·볼륨 연결까지 프로비저닝하고, Profile CRD를 만들면 네임스페이스+자원쿼터+RBAC가 한 번에 생성됨 노트북 생성·팀별 격리를 직접 구현하지 않고 선언(CRD)만으로 처리. 업계 표준이라 원청 환경과 호환
Kubeflow Pipelines (KFP) + Argo 학습 워크플로우 엔진. 파이프라인 정의(YAML)를 올리면 Argo가 단계별 컨테이너를 순서·의존성에 맞게 실행. 실행 이력·아티팩트는 내장 MySQL·MinIO에 기록 "데이터 준비→학습→평가→포장→배포" 자동화와 스케줄 재학습(cron)이 표준 기능으로 제공됨
Katib 하이퍼파라미터 자동 탐색(HPO). Experiment CRD에 탐색 범위를 선언하면 Trial(학습 Job)을 반복 실행하며 최적값을 수렴 탐색 알고리즘·병렬 실행·조기 중단을 직접 구현할 필요가 없음
KServe 모델 서빙 표준화. InferenceService CRD에 모델 위치(s3://)와 형식만 선언하면 추론 서버 기동·버전 교체·자원 관리·표준 예측 API(v1)를 제공 sklearn·PyTorch·LLM(vLLM)을 같은 방식으로 배포·관리 — 포털 화면 하나로 통합 가능
vLLM LLM 전용 고성능 추론 엔진. KServe의 ServingRuntime으로 등록해 일반 모델과 동일한 절차로 배포. TTFT·TPOT·KV cache 등 LLM 표준 메트릭을 자체 노출 PagedAttention 기반으로 GPU 메모리 효율이 높고, ETRI 검토 지표를 실측으로 제공
MinIO (S3 호환) 데이터셋·학습 산출물·서빙 모델의 단일 저장소. 파이프라인이 쓰고 KServe가 읽는 접점 S3 API 호환이라 운영 전환 시 주소만 바꾸면 사내 스토리지·AWS S3로 대체
NVIDIA device plugin 각 노드의 GPU를 K8s 자원(nvidia.com/gpu)으로 등록해 스케줄러가 장수 단위로 배분하게 함. time-slicing 설정으로 GPU 한 장을 논리 2슬롯으로 광고 — LLM 서빙과 노트북 학습이 같은 GPU를 공유 (deploy/nvidia-device-plugin-timeslicing.yaml) K8s 표준 확장점이라 NPU(리벨리온)도 같은 방식의 플러그인으로 추가 가능. MIG(하드웨어 분할)는 A100/H100 전용이라 개발 장비에서는 time-slicing이 대안 — 메모리·성능 격리는 없으므로 vLLM 점유율을 제한해 공존시킴
CMP 백엔드 (신규 개발) 포털과 클러스터 사이의 번역기. 화면의 클릭을 CRD 생성·패치로 바꾸고, 클러스터 상태·실측 메트릭을 화면용 JSON으로 가공. IDE 접속 프록시(HTTP+WS)와 세션 인증도 담당 — 70개 API Kubeflow 원본 대시보드를 쓰지 않고 openKcloud 포털 UX에 맞춘 화면을 제공하기 위한 접착 계층. 운영 전환 시 인증·라우팅만 Istio/oauth2-proxy로 교체

  1. IDE 라우팅·인증을 Istio + oauth2-proxy로 교체 (현재 자체 프록시+세션 — 동일 아키텍처 위치)
  2. IAM 연동 (현재 데모 계정 2개) · API 엔드포인트 인증 확대
  3. 모델 저장소 MinIO/S3 정식화 · Portal DB(사용자·과금·감사)
  4. NPU(Rebellions)·PIM: 디바이스 플러그인+SDK 이미지 확보 시 동일 구조로 확장 — 벤치마크 표에 실측 열 추가
  5. 공유 스토리지 도입 — 현재 노드 로컬(local-path)이라 볼륨이 노드에 고정됨. NFS·Ceph 전환 시 노트북을 어느 노드에서든 재개 가능 (볼륨이 놓인 노드의 GPU가 선점되면 다른 노드 GPU가 남아도 못 쓰는 제약도 함께 해소)
  6. 원격 워커 노드 연결 안정화 — Windows/WSL 워커 노드는 유휴 시 kubelet 스트리밍이 끊기는 사례가 있어 keepalive 예약작업으로 잡아둔 상태. 운영 전환 시 표준 리눅스 노드로 대체하면 해소
  7. GPU 분할(MIG) 적용 — A100 도입 시 한 장을 최대 7개로 나눠 격리된 다중 사용자 동시 사용 (개발 장비에는 격리 없는 time-slicing 공유를 이미 적용 — MIG로 승격되는 자리)
  8. 파이프라인 실행 파라미터 입력 UI — 백엔드는 지원하나 화면 미연결. HPO가 찾은 값을 화면에서 바로 넣어 재학습하는 흐름 완성 필요
