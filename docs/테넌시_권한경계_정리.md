# 테넌시 · 권한 경계 정리 (IaaS / PaaS 서비스 클러스터 / AI 노트북)

작성: 2026-10-15 · 목적: 모듈별 권한 경계가 달라 "서비스 클러스터 공유 시 권한 분배"가 애매한 문제를 정리하고 방향을 결정한다.

## 1. 기본 전제

사용자는 **자신이 속한(iam_project_member) 프로젝트의 자원만** 요청·조회·운영한다. 관리자는 전체.
그런데 "프로젝트"가 각 모듈에서 **무엇으로 실현되는지**가 달라서, 공유 클러스터에서 경계가 흐려진다.

## 2. 현재 3개 모듈의 권한 경계 (실제 구현 기준)

| 모듈 | 경계 단위 | 스코프 방식 (코드) | 격리 수준 |
|---|---|---|---|
| **IaaS** | OpenStack **프로젝트** | `iam_project_member` → 내 프로젝트만. OpenStack이 프로젝트 격리를 네이티브 강제 | 깔끔 |
| **PaaS 서비스 클러스터** | **클러스터(소유 프로젝트)** | Magnum 클러스터의 `project_id` 가 내 프로젝트 멤버십에 있으면 노출 (`cluster-scope-bar.tsx`: `myProjectIds.has(c.projectId)`) | 클러스터 단위만. **내부 네임스페이스/워크로드는 프로젝트별로 안 나뉨** |
| **AI 노트북 (Kubeflow)** | **네임스페이스(Kubeflow Profile)** | Profile 라벨 `openkcloud.io/project-id` = 프로젝트 **1:1**, 내 프로젝트 Profile만 | 네임스페이스 단위 격리 |

## 3. 문제: 서비스 클러스터를 여러 기관/프로젝트가 공유할 때

현재 PaaS 는 **"클러스터 1개 = 소유 프로젝트 1개"** 전제다. 공유하면 두 가지가 깨진다.

1. **소유권 충돌** — 클러스터가 프로젝트 A 소유이면 B 사용자는 볼 수 없다. 보이게 하려고 전원을 A에 넣으면 프로젝트 격리가 무너진다.
2. **내부 미분할** — PaaS 워크로드/서비스/스토리지 화면은 **클러스터 전체(또는 선택 네임스페이스)** 를 조회·조작한다. 공유하면 **B가 A의 워크로드를 모두 보고 건드릴 수 있다.** 클러스터 내부를 프로젝트별로 나누는 장치가 없다.

## 4. 이미 있는 "정답 방향" — 노트북의 프로젝트↔Profile 1:1

협의된 **"OpenStack 프로젝트 ↔ Kubeflow Profile 1:1"** 이 바로 공유 클러스터 다기관 문제의 표준 해법이다.
Kubeflow Profile = **네임스페이스 + RBAC + ResourceQuota** 이므로:

- 공유 클러스터 하나 위에 **프로젝트마다 네임스페이스(Profile)** 를 둔다.
- 사용자는 **자기 프로젝트의 네임스페이스만** 접근한다.

→ **"네임스페이스를 테넌트 경계로"** 하는 모델. 노트북은 이미 이 모델이고, **PaaS 일반 워크로드는 아직 클러스터-소유 모델**이라 둘이 어긋나 있다. 이것이 "정리가 안 되는" 근본 원인.

## 5. 결정해야 할 것 — 서비스 클러스터의 테넌트 경계

- **A. 네임스페이스 = 경계 (권장 · 노트북과 통일)**
  공유 클러스터 + 프로젝트↔네임스페이스 매핑. PaaS 워크로드/서비스/스토리지 조회·조작을 **그 매핑으로 스코프**(현재 클러스터 단위 → 네임스페이스 단위). 다기관 공유 가능, 격리 확보.
  - 필요한 일: ①프로젝트↔네임스페이스 매핑 저장소 ②목록/상세/쓰기 API에 네임스페이스 스코프 가드 ③사용자는 자기 네임스페이스만, 관리자는 전체.
- **B. 클러스터 = 경계 (현재 유지)**
  프로젝트/기관마다 전용 클러스터. 단순·확실하지만 **공유 불가**, 자원 낭비.
- **C. 혼합**
  일부는 전용(B), 일부는 공유(A: 네임스페이스 스코프).

노트북이 A를 따르므로 **A로 통일**하는 것이 일관적이다.

## 6. 미결 질문 (회의 안건)

1. **방향**: A / B / C 중 무엇으로 갈 것인가?
2. **매핑 관리 위치**: 프로젝트↔네임스페이스 매핑을 **포털 DB(MNT-CORE)** 에서 관리할 것인가, **클러스터 라벨/어노테이션**(노트북이 쓰는 `openkcloud.io/project-id` 방식)에서 읽을 것인가?
3. **네임스페이스 생성 주체**: 네임스페이스(+RBAC+Quota)를 누가 언제 만드나? (노트북은 워크스페이스 신청→프로비저닝으로 Profile 생성. PaaS 도 동일 신청 흐름에 태울 것인가?)
4. **멀티 서비스 클러스터**(별도 과제, 외주 설계 요청 중)와의 관계: 클러스터가 여러 개 + 각 클러스터 안에서 네임스페이스 스코프. 두 축(클러스터 선택 × 네임스페이스 스코프)을 어떻게 조합할지.
5. **RBAC 강제 지점**: 지금 PaaS 스코프는 프론트 필터 위주다. 공유 테넌시에서는 **백엔드에서 네임스페이스 접근을 강제**해야 안전하다(프론트 필터만으로는 불충분). 어느 수준까지 서버 강제할 것인가?

## 6-1. 채택 방향 (2026-10-16 결정 · 구현 착수)

**옵션 A(네임스페이스 경계)로 가되, 1단계로 "클러스터 가시성"부터 구현한다.**

- **매핑 저장**: 포털 DB `paas_project_cluster` 테이블(프로젝트↔클러스터 N:N). 키는 `project_id`(불변 UUID), 표시명은 조인. `namespace` NULL=전용(클러스터 전체), 값=공유(그 네임스페이스만).
- **1단계(구현함) — 가시성**: 클러스터 목록을 전체 조회한 뒤, 사용자는 **내 프로젝트에 매핑된 클러스터만** 노출. 소유 `project_id` 기준(기존) → **매핑 기준**(`/my-cluster-ids`)으로 전환. 관리자는 전체.
- **1단계 — 관리 화면**: 클러스터 상세 모달 안 "접근 프로젝트" 섹션(관리자 전용)에서 프로젝트 추가/회수(+공유 시 네임스페이스). `paas_project_cluster` CRUD.
- **2단계(다음) — 내부 격리**: 워크로드/서비스/스토리지 조회·쓰기를 매핑의 `namespace` 로 스코프. ⚠️ **백엔드에서 네임스페이스 접근을 서버 강제**해야 안전(현재 프론트 필터만으론 URL 직접호출 우회 가능). 미결 질문 5번과 연결.

**API (MNT-CORE)**
- `GET /clusters/{id}/access` — 클러스터 접근 프로젝트 목록(관리 화면)
- `POST /clusters/{id}/access` (admin) — 부여 `{projectId, namespace?}`
- `DELETE /clusters/{id}/access?projectId=&namespace=` (admin) — 회수
- `GET /my-cluster-ids` — 내가 접근 가능한 클러스터 ID(사용자 가시성)
